# 项目问题分析（内存方向）

基于当前仓库状态（`开发进度.md`、`WorkbenchModel+Residency`、`SessionModel`、`TimelineWindow`、`RenderCaches`、`EngineWarmPool` 等）的分析。Plan 模式下只给分析与建议，不修改文件。

## 一、多会话内存占用的主要来源

1. **每个「活」会话对应一个 Agent 子进程（claude 等）**  
   - `EngineWarmPool` 注释里明确：每个待命进程约占 **0.3~0.4 GB**。  
   - 驻留策略 `SessionResidencyPolicy` 只休眠「不可见 + 可休眠」的会话；**当前可见标签页里的会话永远不会休眠**。  
   - 默认 `maxLiveSessions = 3`、`idleHibernateMinutes = 10`，且 `canHibernate` 有大量前置条件（运行中、有排队/权限/提问、终端在跑、工具进行中、无法 resume 的引擎等），很容易让会话**长时间保持活进程**。  
   - 终端（`TerminalStore` 每标签持有）、LSP（默认最多 4 个工作区）、浏览器标签页（`WKWebView`）也各自占内存，且不是会话休眠时统一回收的对象。

2. **时间线数据并不因「窗口化渲染」而释放**  
   - `TimelineWindow.slice` 只是渲染层折叠最近 40 轮，`timeline.entries` 仍保留全部历史。  
   - `SessionArchive` 打开时默认只回显最近 40 轮，但 `loadEarlierArchive()` 会重新渲染全部；用户点「显示更早」后内存就会长期持有完整历史。  
   - 图片/大工具结果作为内容块留在条目里，不会自动裁剪。

3. **全局缓存常驻**  
   - `MarkdownCache`：`countLimit=400`、`totalCostLimit=24MB`，但 `states`/`lastMissText` 等静态状态随进程常驻。  
   - `MermaidSceneCache`：120 个场景。  
   - `RenderCaches`、`TabKeepAlive`（LRU 保活标签视图）都会在切换标签时保留视图/状态，减少重建但增加驻留内存。

4. **无界缓冲**  
   - `ACPKit/Transport.swift`、`ACPConnection`、`LSPTransport` 等多处 `AsyncStream.makeStream(bufferingPolicy: .unbounded)`。如果消费者跟不上生产者，积压会持续增长（仓库已有 `StreamBacklog` 计数器，但只是观测，不是限流）。

5. **休眠判定的保守策略**  
   - `canHibernate` 在 `agentPID != nil` 时要求 `shellActivityProbe` 在 90s 内刷新且无 shell；缓存缺失/过期直接不休眠。`refreshShellActivities()` 每 30s 在后台跑 `proc_listchildpids`，但若 probe 过期或进程树探测失败，会话就永远不休眠。

## 二、现有机制的缺口

- **内存压力只收紧策略，不主动释放缓存**：`underMemoryPressure` 时 `residencyLimits.underPressure` 把空闲阈值压到 1 分钟、`maxLive=1`，并 `warmPool.discardAll`；但不会清理 `MarkdownCache`/Mermaid 缓存、不会卸载已挂载的标签视图、不会裁剪 `timeline.entries`。  
- **休眠只结束 Agent 进程，不释放时间线/草稿/标题**（设计如此，但大历史仍常驻）。  
- ** warm pool 容量 2** 在「全部」模式下会额外起 2 个进程，叠加多会话场景。  
- **`TabKeepAlive` 保活**在多标签场景下会保留更多视图树（含代码高亮、Mermaid、图片）。  
- 开发进度里还标有「`SessionModel` 拆分受 `private` 依赖限制暂缓」，大文件（2628 行）意味着状态集中、排查内存泄漏成本高。

## 三、建议的改进方向（按投入/收益）

### A. 进程层（收益最高）
- 把「可见会话」也纳入休眠候选，但仅在**内存压力**或**空闲超时**时休眠，唤醒时恢复（已有 `wake()`/`dormantSessionId` 机制）。  
- 为每个会话增加「挂起时释放时间线中的大块内容（工具输出/图片），保留元数据，展开时按需重载」。  
- 降低默认 `maxLiveSessions`（如 2）与 warm pool 容量（如 1），并把 warm pool 设为可关闭（已有 `off` 模式）。  
- 终端/LSP 的空闲回收阈值对齐会话驻留（LSP 已有空闲回收，终端可加）。

### B. 数据层
- `timeline.entries` 增加「软上限」：超过 N 轮/字节时把更早轮次序列化到 `SessionArchive` 并从内存移除，展开时再加载（类似 `archiveHidden` 但支持多次卸载）。  
- 工具结果/图片内容块在折叠后释放字节，仅保留占位。  
- `SessionArchive.load` 已支持窗口化，确保 `openFromArchive` 默认 `keepTurns` 不被覆盖为 `nil`。

### C. 缓存层
- 给 `MarkdownCache`/`MermaidSceneCache` 注册到 `GaugeRegistry` 并在内存压力时 `removeAllObjects()`（NSCache 自动驱逐不可靠时主动清理）。  
- `TabKeepAlive` 在内存压力时降为 0 或 1，强制重建非活动标签。  
- `StreamBacklog` 超阈值时对生产端做背压（或至少告警 + 丢弃可恢复的增量）。

### D. 可观测性（先做，便于验证）
- 在「演示指标」/诊断页暴露：活进程数、各会话 `entries` 数/字节估算、缓存命中/容量、StreamBacklog 深度、warm pool 数量。  
- 用 `Scripts/demo-bench.sh` 增加「多会话内存」场景（打开 N 个会话、切换、休眠前后采样），把内存作为预算门槛。  
- 用 Instruments Allocations/Leaks 对「打开 10 个会话 → 切换 → 关闭」做一次基线，确认是否有泄漏（强引用、未取消的 `Task`、`@State` 持有视图）。
