下表「目标」是设计预算,**不等于已达成**;「实测」只列文档与脚本里有记录且可复现的数据(口径与复测命令见 §3)。

## 2. 设计手段(均可在代码中核实)

1. **启动**:设置与历史异步加载;登录 shell 环境解析后台执行并缓存;会话标签首次显示才恢复(`pendingRestores`)。
2. **并发**:I/O、解码、diff、配置解析在后台 actor;主线程只应用快照;工作台落盘的编码与写盘在后台(`SaveSequencer`)。
3. **合并**:事件合批窗口 16ms 起,按主线程处理耗时自适应、上限 80ms(`EventCoalescer`/`AdaptiveWindow`);滚动跟随每帧至多一次(`FrameCoalescedAction`)。
4. **虚拟化与窗口化**:时间线是 SwiftUI `LazyVStack`,并只挂载最近 40 轮(`TimelineWindow`,「显示更早的 N 轮」翻页);浏览器标签上限 8 个、标签 LRU 保活(`TabKeepAlive`)。
5. **编辑器**:超过行数阈值进入大文件模式(关闭自动换行、仅高亮视口附近,`CodeEditorView.largeFileLineThreshold`);高亮结果缓存,流式代码块增量高亮。
6. **缓存**:Markdown、高亮、Mermaid(64 条 LRU)、图片等缓存均有上限。
7. **进程**:会话休眠与驻留(`SessionResidencyPolicy`)、待命池容量 2(`EngineWarmPool.capacity`),见优化记录 §4。
8. **GPU/动画**:玻璃只用于功能区,按钮组用 `GlassEffectContainer`;持续动画用 Core Animation 层并经 `OMAnimationGate` 门控。

## 3. 度量方法

- **Instruments**:`xctrace`/Instruments 的 App Launch、Time Profiler、Animation Hitches、Allocations;`Log.perf.span` 同时发 signpost(Points of Interest 轨道)。
- **内存**:`footprint -p <pid>` 与 `vmmap`;`Scripts/perf.sh [次数]`(需先 `Scripts/bundle.sh release`)多次冷启动测「进程启动→首帧」并采样空载内存。
- **UI 基准**:`Scripts/perf-ui.sh [interact|cpu|resize|drag|scroll|stream|all] [--build] ...`(演示模式,release 验收),汇总由 `perf-report.py ui` 完成。
- **浸泡回归**:`Scripts/perf-soak.sh [秒数] [场景]`(演示模式灌入「回归全集」,检查内存峰值/前后半程增长/单次卡顿);`OMA_CI_PERF=1 Scripts/ci.sh` 接入 CI。阈值环境变量 `SOAK_MAX_MB`(600)、`SOAK_MAX_DRIFT_MB`(80)、`SOAK_MAX_HITCH_MS`(1500)。
- **微基准**:`StreamingRenderBenchTests`(流式渲染),`Scripts/test.sh --filter StreamingRenderBench`。
- **卡顿取证**:`OMA_HITCH_SAMPLE=1`(`HitchStackSampler`),主线程卡顿 ≥250ms 时调用 `/usr/bin/sample`,日志 WARN「卡顿栈」。

## 4. 日志观测(先看日志,不必先开 Instruments)

日志目录 `~/Library/Logs/OhMyAgent/`,每行带 `pid`(开发版与安装版共用目录,按 pid 区分)。

```bash
Scripts/logs.sh report        # 最近一次启动的整体画像
Scripts/logs.sh mem           # 内存/CPU 时序
Scripts/logs.sh slow          # 所有慢操作与卡顿
Scripts/logs.sh turn 1faaa441 # 某会话(前 8 位)的全链路
# 加 --all 看全部日志,--pid N 指定进程
```

### 4.1 日志一览(分类 `perf`,除特别注明)

| 消息 | 频率 | 关键字段 | 用途 |
|---|---|---|---|
| `资源采样` | 每 30s | footprintMB / peakMB / cpuPct / threads / fds / childMB / agentMB / lspMB / terminalMB | 内存与 CPU 曲线,子进程按角色汇总 |
| `容量快照` | 每 30s | timeline.* / sessions.* / cache.* / backlog.* / lsp.running / engine.standby | 哪类数据在增长 |
| `性能汇总` | 每 5 分钟与退出 | name / count / totalMs / p50Ms / p95Ms / maxMs | 时间累计花在哪 |
| `会话汇总` | 退出 | uptimeSec / peakMB / hitches / topSpans | 一次运行的总览 |
| `内存增长较快` / `内存占用偏高` / `CPU 持续偏高` | 触发时 WARN | 同资源采样 + deltaMB / topSpans / busyChildren | 自动告警 |
| `主线程卡顿` | ≥100ms WARN | ms / total / recent=最近完成的跨度 | 卡顿时刻主线程在做什么 |
| `启动阶段` | 启动 | stage / sinceLaunchMs | 启动各段耗时 |
| `首个输出` / `轮次结束`(session) | 每回合 | ttftMs / ms / chunks / tools | 首 token 时间与回合规模 |
| `代理流结束` | 每个模型请求 | route / wire / outcome / firstChunkMs / chunks / bytes / totalMs / convertMs | 慢在上游还是本地转换 |
| `<操作> 耗时较长` | 超阈值 WARN | ms + 上下文 | 单次慢操作 |

跨度阈值:事件批处理 16ms、时间线分组 8ms、Markdown 解析 8ms、保存工作台状态 30ms、记录最近会话/读注册表 16ms、会话记录解析 300ms、LSP 请求 500ms、git 命令 500ms、时间线挂载 120ms、历史回放 800ms。

### 4.2 速查:现象 → 看哪里

| 现象 | 先看 | 判断 |
|---|---|---|
| 内存越用越高 | `logs.sh mem` 的本进程 / 子进程两列;`report` 的「前后半程均值差」 | 本进程涨:看 `容量快照` 里 timeline.entries / textKB / imageKB / cache.*;子进程涨:看 agentMB(引擎自己的上下文,App 控制不了) |
| 关掉会话内存不回落 | `sessions.count`、`timeline.entries` 是否回落 | 不回落 = 会话对象未释放(泄漏嫌疑) |
| 流式输出时卡 | `主线程卡顿` 的 `recent=`;`cache.markdown.streamReparse` | streamReparse 应为 0(已做增量解析);持续增长 = 续解析状态被打断 |
| 流式输出时 CPU 高 | `CPU 持续偏高` 的 topSpans;`性能汇总` 里 Markdown 解析 / 时间线分组 | 看哪个跨度累计最大 |
| 发消息后迟迟不出字 | `首个输出.ttftMs` + `代理流结束.firstChunkMs` | firstChunkMs 大 = 上游模型慢;ttftMs 远大于 firstChunkMs = 本地链路慢 |
| 事件处理跟不上 | `backlog.events.depth/peak`、`backlog.acpLines.*` | depth 持续 > 0 = 消费者跟不上,内存会涨 |
| 启动慢 | `启动阶段` | 见 §1 启动完成一行 |
| 某操作偶发卡 | `slow` + `主线程卡顿.recent=` | recent 里耗时最大的跨度就是元凶 |
| Git/LSP 慢 | `git 命令较慢`、`LSP 请求 耗时较长` | 含命令与方法名 |

### 4.3 开关与配置

| 项 | 方式 |
|---|---|
| 资源采样间隔 | 设置 → 诊断 → 性能;或 `OMA_PERF_SAMPLE_SECONDS`(0 关闭,5–600) |
| perf 详细日志 | 设置 → 诊断 → 性能;或 `OMA_LOG_LEVEL_PERF=debug`;任意分类 `OMA_LOG_LEVEL_<分类>` / 偏好 `log.level.<分类>` |
| 全局日志级别 | 设置 → 诊断 → 日志;或 `OMA_LOG_LEVEL` |
| 诊断包 | 设置 → 诊断 → 导出诊断包(含「性能画像」:footprint 时序与耗时 Top 10) |

### 4.4 代码入口

- `OMLog/PerfTrace.swift`:`Log.perf.span / timed`、`MainThreadHitchMonitor`;`PerfStats.swift`:耗时聚合;`ResourceSampler.swift`:资源采样与告警。
- `OMLog/ProcessRegistry.swift`:`ProcessRegistry`(子进程登记)、`GaugeRegistry`(容量指标)、`StreamBacklog`(流积压);`CorrelationID.swift`:`sid / turn / req / tcid`。
- `OhMyAgentApp/PerfGauges.swift`:容量指标注册;`LaunchTrace.swift`:启动打点。
- 新增容量指标:`GaugeRegistry.shared.register("模块.含义") { 当前值 }`(主线程读取用 `registerMain`)。新增耗时:`let span = Log.perf.span("名称", warnMs: 16, quiet: true); defer { span.end() }`。

## 6. CI 门槛(如实记录)

- 已落地:`Scripts/ci.sh` 本地化扫描、UI 规范扫描、零警告构建(`-warnings-as-errors`)、全部单元/协议测试、plist/strings 校验。
- 可选(`OMA_CI_PERF=1`):release 构建后 `perf-soak.sh` 浸泡,按 §3 阈值失败。
- `perf-report.py ui` 对侧栏切换/冷打开/热切换/运行 CPU 有绝对阈值(如点击→首帧 P95 ≤120ms、运行 CPU ≤15%),由 `perf-ui.sh interact|cpu` 使用;`resize|drag|scroll|stream` 目前只记录不设门槛。
- **未落地**:原设想的「性能基线回退超过 15% 即失败」。`Scripts/perf.sh` 只打印首帧序列与空载内存,不比对基线、不设退出码;仓库中没有基线对比机制,现有门槛均为绝对阈值。
- 实测数据的记录位置:`开发进度.md` 的 M8 门槛表与后续优化条目;目标与实测差距过大时需在文档中记录口径调整及原因。
