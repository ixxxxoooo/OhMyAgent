## 引子：在 Web 的时代，为什么还要原生

过去两年，几乎所有 AI 编程工具都长着同一张脸：一个 Electron 外壳，左边文件树，中间对话框，右边预览窗；底下跑着 Node，上面套着 React，再包一层 WebView。这套方案并不难看，甚至相当高效——前端生态成熟，迭代速度快，跨平台几乎免费。于是当我们要做 OhMyAgent 时，第一个被反复追问的问题就是：为什么不用 WebView？

答案不在于“原生更高级”这种审美判断，而在于这个产品的交互密度。Agent 工作台不是聊天框，它是一个正在进行中的工程现场：模型在流式输出，工具在读写文件，终端在滚动，Diff 在刷新，用户在输入中文，权限对话框随时可能弹出。所有这些事情必须同时发生，而且必须在几十毫秒内被看见。Web 技术当然也能做到，但每一层抽象都会在某个极端场景里收取代价：中文输入法的组合态、上千条消息的滚动、跨窗口的焦点管理、系统级快捷键、文件拖拽、无障碍朗读、主题切换时的大面积重绘。我们想要的不是“能用”，而是“像系统的一部分”。

于是有了 OhMyAgent：Swift 6 + SwiftUI + AppKit，没有 WebView，通过 ACP（Agent Client Protocol，基于 stdio 的 JSON-RPC）接管本机已经安装好的 Claude Code。它不重新实现模型，不重新实现工具，也不做账号登录——模型、凭据、工具链、MCP 全部复用本机已有的能力。我们只做一件事：把这个能力装进一个足够快、足够稳、足够像 macOS 的壳里。

这篇文章想把这个“壳”拆开，谈谈里面的结构、边界、踩过的坑，以及那些看起来不起眼、但决定了产品质感的工程细节。

## 一、问题定义：Agent 工作台到底在解决什么

在写第一行代码之前，我们把需求拆成了三个层次。

第一层是“会话”。用户需要一个地方提出问题、看到回答、继续追问。这一层看起来最简单，实际上最容易被低估。流式输出不是把字符串追加到屏幕上那么简单：它要求时间线在高速更新时保持稳定，要求代码块在未闭合时也能正确渲染，要求用户在模型输出过程中仍然可以滚动、复制、选中、插入新消息。一个卡顿的流式界面，会让再聪明的模型显得迟钝。

第二层是“行动”。Agent 与聊天机器人最大的区别，是它会调用工具：读文件、改代码、跑命令、查 Git、访问 MCP。每一次工具调用都是一次状态迁移：开始、进行中、成功、失败、被拒绝、被取消。用户需要知道它做了什么、为什么这么做、改动了哪里、能不能撤销。工具调用的可视化不是装饰，而是信任的基础。没有这层可视化，用户面对的就是一个黑箱。

第三层是“现场”。一个真实的开发任务从来不在真空中发生：它属于某个项目、某个分支、某个工作区，伴随着终端、编辑器、Diff、搜索、Git 状态和一堆打开着的标签页。Agent 不能是一个漂浮在系统里的聊天窗口，它必须嵌入工作现场，知道当前在哪、改了什么、下一步该看哪里。

这三层需求决定了架构的形状：会话层需要稳定的状态模型与高效的渲染管线；行动层需要一套可靠的进程与协议基础设施；现场层需要一个能持久化、能恢复、能并发的工作台模型。三者不能混在一起，否则任何一个局部的改动都会引发全局的震荡。

## 二、原生的代价与回报

先把代价说清楚。选择原生意味着放弃跨平台，放弃成熟的前端组件生态，放弃“改一行 CSS 就能上线”的迭代速度。SwiftUI 在复杂列表、精细布局和文本编辑上的坑，一点都不比 Web 少；AppKit 桥接带来的心智负担，也远高于写一个 div。团队规模小的时候，这些成本是实打实的。

但回报同样具体。

**输入法。** 中文输入是天然的试金石。Web 输入框在处理组合态（composition）时，经常出现候选词吞键、光标跳动、拼音被提前提交的问题；而在 NSTextView 里，marked text 是一等公民，输入法、撤销、选择、拖拽都有系统级的正确行为。对于一个中文用户每天要敲几千字的工具，这不是细节，是生死线。

**焦点与键盘。** 工作台里有大量快捷键：切换会话、打开搜索、跳转标签、接受补全、中断生成。原生应用有真正的菜单栏、命令系统和焦点链，快捷键不会和浏览器抢，弹窗不会因为失焦而消失，输入法状态不会在窗口之间错乱。

**长列表。** 一个跑了三小时的会话，可能有上万条时间线条目。Web 方案通常要靠虚拟列表加高度测量，而高度测量本身在流式内容下极不稳定。原生列表配合稳定的条目身份、增量解析和折叠策略，能把这件事做得更可控。

**系统集成。** 拖拽文件、在 Finder 中显示、读取剪贴板里的图片、响应系统主题、遵循“减弱动态效果”、支持 VoiceOver、使用 Liquid Glass——这些能力在 WebView 里要么没有，要么需要一层层桥接，要么行为与系统不一致。

**离线与安全。** 没有远程页面，就没有远程代码执行面；没有浏览器内核，就没有一整个需要持续打补丁的攻击面。对于一个能读写本地文件、执行 shell 命令的工具，这一点尤其重要。

所以我们的结论是：原生不是情怀，而是一笔只在特定条件下划算的交易——单平台、高交互密度、强系统集成、对延迟敏感。离开这些条件，Electron 仍然是更理性的选择。技术选型没有立场，只有约束。

## 三、架构总览：用模块边界对抗复杂度

OhMyAgent 的源码按职责切成若干个 SwiftPM target，依赖方向尽量单向（下图为简化示意，只画主干，完整依赖见 `Package.swift`）：

```
ACPKit        协议、JSON-RPC、ACP 模型、场景引擎
   ↑
AgentHost     子进程、工具链定位、Agent 注册表、Bridge
   ↑
ChatKit       会话模型、时间线、补全、命令、提供商模型（同时依赖 CanvasKit）
   ↑
WorkbenchKit  多项目、会话树、布局、标签保活、面板状态
   ↑
OhMyAgentApp  SwiftUI / AppKit 视图

CanvasKit     画布文档模型、解析校验、落盘（无视图；ChatKit 与 DemoKit 依赖它）
```

旁边还有一组横向的基础模块：`DesignSystem` 提供颜色、字体、圆角、材质与控件；`IconKit` 提供图标；`DiffKit`、`EditorKit`、`GitKit`、`LSPKit`、`MermaidKit`、`SpreadsheetKit` 各自封装一种能力；`CanvasKit` 承载画布（Canvas）的文档模型；`ProviderProxyKit` 承载本地网关与模型代理；`AutomationKit` 负责任务调度；`DemoKit` 负责演示环境。

这条依赖链有一个刻意的约束：**越靠下的模块越不知道 UI 的存在**。`ACPKit` 不知道什么是会话标签，`ChatKit` 不知道侧栏有多宽，`WorkbenchKit` 不知道颜色令牌。这样做的直接好处是可测试性——协议解析、时间线合并、布局计算、路由匹配都可以在没有窗口的环境里跑单元测试；间接好处是防止“顺手在视图里写业务逻辑”这种腐化。

新增一个模块时，我们要求同时更新模块地图与代码索引。这不是形式主义。一个几十个 target 的工程，最大的成本不是写代码，而是三个月后重新进入时，花半天搞不清楚某个能力到底在哪一层。文档如果不能在导航上省下时间，它就没有存在的价值。

模块边界也不是一次画好的。它随着功能演进而移动：某个能力最初放在视图层，等它长出第二、第三个使用者时，才值得下沉为独立模块。过早抽象会让接口空转，过晚抽象会让依赖纠缠；我们更愿意在第二次复用时重构，而不是在第一次实现时预测未来。

## 四、ACP：把 Claude Code 当作引擎

OhMyAgent 不实现自己的 Agent 循环。它启动本机的 `claude` 进程，通过 stdio 上的 JSON-RPC 与它对话。这个协议就是 ACP。请求与响应是标准的 JSON-RPC 2.0，通知则是单向的流式事件；一条消息一行 JSON，读取端按行分帧，写入端负责序列化与刷新。

选择“接管现有 CLI”而不是“自己实现 Agent”，是一个关键决策。好处非常实际：模型选择、上下文压缩、工具权限、MCP 接入、子 Agent、斜杠命令、会话恢复，这些能力全部由上游维护；我们不需要追着模型 API 的每一次变化跑，也不需要在本地重建一套工具执行沙箱。我们承担的风险则集中在另一侧：协议会演进，进程会崩溃，版本会不一致。

因此，协议层被设计成“薄而严格”。薄，是指它只负责连接、请求编号、超时、取消和事件分发，不掺业务判断；严格，是指所有进出数据都必须经过模型解码，未知字段被忽略，未知事件被记录而不是崩溃。连接本身是一个 actor：

```swift
actor ACPConnection {
    private let process: Process
    private var nextID = 0
    private var pending: [Int: CheckedContinuation<Data, Error>] = [:]

    func request(_ method: String, _ params: Data) async throws -> Data {
        let id = nextID
        nextID += 1
        // 写入一行 JSON，登记 continuation，等待对应的 response
        // 超时、进程退出、取消都会以明确错误结束等待
    }
}
```

上面是**示意代码**，并非源码摘录（实际类型见 `ACPKit` 的 `ACPConnection`/`ACPClient`），省略了细节，但原则是完整的：**每一个请求都必须有确定的归宿**。超时要结束等待，进程退出要结束等待，用户取消也要结束等待。最糟糕的实现是让 continuation 永远悬挂——它不会立刻报错，只会在几分钟后表现为“界面卡住了”，然后花掉一整天去定位。

会话生命周期大致是：初始化连接，创建或恢复会话，发送用户输入，接收流式更新，处理工具权限请求，等待回合结束。流式更新里包含助手文本增量、思考内容、工具调用开始与结束、计划变更、用量统计等。我们把这些事件映射成时间线条目，而不是直接把原始 JSON 丢给视图。这一层映射是产品体验的核心：同样的 `tool_call`，在界面上可能是一张文件编辑卡、一条终端命令卡、一次搜索卡，或者一个未知工具的兜底卡片。

权限请求必须被当作一等公民。Agent 能读文件、能执行命令，这意味着每一次授权都是一次真实的安全决策。界面需要展示工具名、关键参数、目标路径，以及“本次允许 / 始终允许 / 拒绝”的明确选项；超时与取消要有确定语义；被拒绝后 Agent 应该收到结构化的错误，而不是静默失败。我们坚持一个原则：**审批界面展示的必须是实际要执行的命令，而不是模型生成的摘要**。摘要可以被诱导，命令不会。

还有一个容易被忽视的问题：工具输出是不可信数据。文件内容、网页内容、命令输出都可能包含“请忽略之前的指令”这类文本。它们必须被当作数据渲染，而不是被当作指令执行。这是 Agent 时代的 XSS，防线不在模型，而在宿主。

## 五、Swift 6 严格并发：把边界画在编译期

这个工程从第一天起就开启 Swift 6 严格并发，并且零警告构建。刚开始会觉得束缚，习惯之后会发现它把大量并发 bug 提前到了编译期。

我们的规则只有几条，但执行得很硬：

**第一，UI 状态属于主线程。** 所有视图模型、工作台模型、时间线存储都标注 `@MainActor`。主线程不做磁盘、网络、子进程阻塞操作。读写文件、解析 JSON、启动进程、等待管道，全部在后台 actor 或独立任务里完成，只把结果以值类型送回主线程。

**第二，跨边界只传值。** 跨并发边界传递的类型必须 `Sendable`。我们尽量传 `struct`、`enum` 和不可变快照，而不是传共享的 class。一个可变引用穿过 actor 边界，等于把锁的责任交给了运气。

**第三，取消是结构化的。** 一个会话的流式读取、标题生成、用量统计、文件监听，都属于同一棵任务树。会话结束时取消根任务，所有子任务随之结束。不要用散落的布尔标志去“通知”后台停止——那种代码在正常路径上看起来没问题，在快速切换会话时一定会泄漏。

**第四，流式更新要合批。** 模型每秒可能吐出几十个增量。如果每个增量都触发一次完整的 SwiftUI 更新，主线程会被无意义的重排淹没。我们的做法是：底层按增量累积，主线程以约一帧的节奏取快照；文本条目保持稳定的身份，只更新内容，不重建视图。用户看到的是连续的字符流，系统看到的是可控的刷新频率。

这里有一个反直觉的经验：**并发问题很少表现为崩溃，更多表现为“偶尔慢一下”**。一次主线程上的同步文件读取，可能只阻塞 20 毫秒，用户不会报告，但它会在滚动、输入、动画叠加时变成可感知的粘滞。严格并发加上“主线程零 I/O”的纪律，价值就在于把这些不可见的抖动消灭在代码 review 之前。

## 六、状态与时间线：让流式内容保持稳定

`ChatKit` 里最重要的两个东西是会话模型和时间线存储。它们遵守一个朴素的原则：**单一可信源，视图只读派生状态**。

会话模型持有身份、标题、工作目录、当前模型、运行状态、排队消息、目标、附件等。时间线存储持有一条按顺序排列的条目数组，每个条目有稳定 id、类型、内容和元数据。视图不直接修改数组，而是调用模型暴露的意图方法：追加用户消息、开始助手回合、追加文本增量、登记工具调用、结束回合、标记错误。这样所有状态迁移都集中在一处，便于测试，也便于持久化。

条目类型看起来琐碎，但它决定了渲染的复杂度：用户消息、助手文本、思考块、工具调用、文件 Diff、终端输出、错误、上下文摘要、计划、子 Agent。每一种都有自己的折叠规则、复制行为、悬停操作和可访问性描述。新增一种条目，必须同时补演示场景——否则覆盖守卫测试会失败。这条规则救过我们很多次：它强迫作者在“能显示”之外，还要回答“在真实会话里长什么样”。

流式渲染最大的坑是身份不稳定。假设每个增量都创建一个新条目，SwiftUI 会认为列表发生了变化，轻则动画错乱，重则整段文本重新布局，滚动位置跳动。我们的做法是：助手回合开始时创建一个条目，之后所有文本增量都追加到同一个条目上；工具调用按调用 id 去重；思考块与正文分开，但同样保持稳定身份。条目的高度也不是每次都重新测量，而是利用文本布局的缓存，只在内容真正变化时失效。

另一个细节是自动跟随。用户在底部时，新内容应该自动滚动；用户往上翻看历史时，绝不能把视角拽回底部。这需要区分“程序滚动”和“用户滚动”，需要在惯性滚动期间抑制自动跟随，还需要在用户回到底部时恢复。听起来像小事，但它决定了长会话能不能被认真阅读。

回合结束同样没有想象中简单。协议会给出明确的结束事件，但现实里进程可能中途退出、网络可能断开、工具可能长时间无响应。我们有一套启发式规则来判断“回合是否已经事实上结束”，用来及时解除“正在输入”的状态，避免界面永远停在等待动画上。启发式不是协议替代品，而是故障时的兜底；它的存在本身就说明，分布式系统里没有“绝对不会发生”。

还有一类状态经常被产品忽略：用户想在 Agent 运行过程中插话。直接打断可能丢掉正在进行的工作，完全不打断又会让用户等很久。我们把它拆成两种意图：引导是在当前回合内追加一条优先级更高的指令，排队的消息则等当前回合结束后再发送；界面上要明确显示消息处于哪种状态，允许撤回和调整顺序。目标（goal）是更长周期的意图，它跨回合存在，用来回答“这一轮到底要完成什么”，并在上下文压缩后仍然保留。把这些状态显式建模，而不是塞进一个字符串数组，才能在恢复会话、切换标签、进程重启之后仍然保持一致。

## 七、渲染管线：Markdown、代码与图表

Agent 的输出天然是 Markdown：标题、列表、表格、引用、代码块、链接，偶尔还有 Mermaid 图。渲染这条链路的目标不是“支持全部语法”，而是“在流式过程中始终可读”。

Markdown 解析采用增量策略：未闭合的代码围栏按代码块处理，未完成的表格先按普通文本显示，链接在闭合后才变成可点击。解析结果按内容哈希缓存，主题切换时只需要重新取色，不需要重新解析。代码高亮单独一层：缓存键包含语言、主题 id 和内容哈希；超大代码块延迟高亮，避免一屏之外的内容拖慢首帧；高亮失败时回退为等宽纯文本，绝不阻塞渲染。

Mermaid 是一个特别的决定。大多数桌面工具会嵌入一个浏览器来渲染图表，我们选择用纯 Swift 实现：解析、分层布局、生成场景、再用 SwiftUI Canvas 或离屏位图绘制。支持的图类型有限——流程图、时序图、状态图、类图、饼图、甘特图——但换来的是完全离线、主题一致、无进程间通信、无 WebView 生命周期问题。渲染器的输入是文本，输出是场景树；布局算法与绘制分离，因此可以在测试里直接断言节点位置，而不需要截图比对。

这条链路里最重要的原则是**降级要优雅**。解析器遇到不认识的语法，应该把原文显示出来，而不是显示空白；高亮遇到未知语言，应该显示纯文本；Mermaid 布局失败，应该显示源码与错误提示。用户可以接受“这里没渲染好”，但不能接受“这里什么都没了”。

图片与附件走另一条路：粘贴或拖拽进来的图片先落到会话的附件目录，时间线里显示缩略图，点击后用原生图片查看器打开。不在内存里长期持有原始位图，是大会话不爆内存的关键之一。

画布（Canvas）是另一类“Agent 产出物”：Agent 通过 Bridge 工具 `canvas_create`/`canvas_update` 提交一份结构化的 JSON 文档，由 `CanvasKit` 宽松解码并带路径地校验，再落盘到应用数据目录；界面用原生块渲染（标题、Markdown、统计卡、表格、图表、提示框、代码、图片、Mermaid、分区），而不是嵌入 React 或 WebView。时间线里只放一张画布卡片，点击后在独立标签页打开。校验错误会带着字段路径返回给 Agent，让它自行修正，这比静默丢弃更容易收敛。

## 八、本地网关：一个监听，多种路由

`ProviderProxyKit` 可能是整个工程里最“反直觉”的模块。它在本机回环地址上开一个 HTTP 服务，同时承担两件事：模型代理与 MCP Bridge。

为什么要模型代理？因为 Claude Code 只会说 Anthropic 的 Messages 协议，而用户可能想用别的提供商。代理的做法是：给每个提供商分配一个路由令牌，令牌放在 URL 路径里；Claude Code 以为自己在访问一个普通的 Anthropic 端点，代理在内部把请求转发给真正的上游。Anthropic 协议的上游直接透传；OpenAI 协议的上游则做一次双向转换：请求侧把 Messages 转成 Chat Completions，响应侧把 SSE 增量、工具调用、结束原因再转回来。图片、思考块、工具结果都有各自的映射规则。

这件事的难点不在“能不能转”，而在“转得有多诚实”。协议之间不是同构的：有的提供商没有思考块，有的对工具调用的并行数量有限制，有的流式事件顺序不同，有的在错误时返回 200 加一段错误文本。代理必须把这些差异收敛成上游能理解的形状，同时把无法表达的信息明确降级，而不是悄悄丢掉。日志只记录路由 id、状态码和耗时，绝不记录请求体、密钥或完整环境变量——这是硬约束，不是建议。

真实密钥只存在于代理进程的内存里。Claude Code 拿到的是路由令牌，不是厂商密钥；令牌可以短生命周期、可以按会话撤销。这个设计的意义在于缩小暴露面：即使某个子进程被诱导打印环境变量，它看到的也只是无意义的本地令牌。

MCP Bridge 则解决另一个问题：Claude Code 通过 MCP 协议访问工具，而我们的工具在应用进程内。传统做法是再起一个辅助进程，通过 stdio 转发；我们选择把 Bridge 直接挂在同一个网关上，进程内调用，省掉一次序列化和一个需要管理的生命周期。一个监听、令牌路由、两类流量，部署与排错都简单得多。

## 九、进程、工具链与“待命池”

AgentHost 负责找到 `claude`、启动它、给它一个干净的环境、把工作目录设为项目根，并在它崩溃时报告。听起来是管道工作，实际上处处是坑。

第一是定位。用户可能用 Homebrew 安装，可能用官方安装脚本，可能放在 `~/.local/bin`，也可能通过版本管理器切换。我们不能假设 PATH 和 GUI 应用看到的一样——从 Finder 启动的进程，PATH 往往比终端里短得多。因此定位逻辑要覆盖常见路径、读取登录 shell 的环境、校验版本，并在失败时给出可操作的提示，而不是一句“找不到命令”。

第二是环境。子进程只需要它该知道的东西：工作目录、必要的 PATH、代理地址与路由令牌。不要把整个父进程环境原样传下去，更不要把厂商密钥塞进环境变量。环境越干净，泄露面越小，行为也越可预测。

第三是生命周期。应用退出时要清理子进程，异常崩溃后要能检测孤儿进程，会话切换时要区分“保留”与“终止”。我们维护一个引擎待命池：提前启动少量进程，降低首个请求的冷启动延迟；池有上限，空闲一段时间后回收；每个进程绑定一个工作目录与会话身份，避免上下文串味。

第三点补充是**休眠与驻留**。每个会话各占一套进程（Node 适配器加 `claude` CLI），实测空闲时每个会话约数百 MB，标签一多内存就线性增长。因此纯函数的 `SessionResidencyPolicy` 会定期从会话快照里挑出该休眠的：运行中、有待处理权限或提问、仍有后台终端、子代理在跑、正显示在标签里的会话一律不动；闲置超过阈值（默认 10 分钟），或存活数超过上限（默认 3），或系统报内存压力时，按最久未用优先休眠。休眠只结束 Agent 进程，时间线、草稿和会话 id 都留在内存里；用户再输入或发送时，用 `session/resume` 唤醒（不回放历史），唤醒期间的发送进入排队。待命池容量也相应收紧到 2。具体数据与取舍见 `20261019_性能优化记录.md`。

第四是可观测性。每个会话、每个请求、每个工具调用都有 id；日志里带 id 与耗时；错误附带上下文而不是只有一句 message。排查问题时，第一件事永远是看日志，而不是猜。日志规范因此必须是强制的：只用统一的日志门面，禁止 `print`，禁止把令牌、Authorization、完整环境变量写进去。

## 十、工作台现场：项目、标签与面板

Agent 会话不是孤立存在的，它总是属于某个项目、某个工作区、某一组打开着的文件。工作台层要解决的，就是把这些关系稳定地表达出来，并且在应用重启后原样恢复。

最基础的单位是项目，项目下面是会话树。一个项目可以有多个会话，每个会话对应一个标签页；标签可以跨项目存在，但始终知道自己属于谁。多文件夹工作区是一个容易被忽略的需求：真实项目经常由多个仓库组成，前端一个目录、后端一个目录、基础设施又一个目录，如果工作台只认“一个根目录”，用户就得在多个窗口之间来回切换。因此我们把工作区建模成一组文件夹，搜索、补全、文件树、Git 状态都以这组文件夹为范围。

标签的策略是“有限保活”。完全保活会让内存随着打开过的会话线性增长；完全不保活则会让每次切换都重新加载、重新解析、重新滚动到原来的位置。我们采用 LRU：保留最近使用的若干个会话视图，超出的释放；释放的是视图与缓存，不是会话数据。会话的转录、草稿、滚动锚点仍然持久化，重新打开时可以恢复到接近原来的状态。这里的关键词是“接近”——精确恢复滚动位置在流式内容下几乎不可能，也不值得追求；让用户回到大致的位置、看到未读标记、知道哪里更新了，才是更合理的目标。

布局是另一个持续演进的区域。终端和输出面板可以放在底部、右侧、左侧，或者作为编辑区的一个标签；项目栏和工具栏可以换边；侧栏宽度、面板高度、编辑区比例都持久化。这些能力听起来只是“摆放”，实际上对几何计算的要求很高：拖拽落点要判断目标区域，分隔条要遵守最小尺寸，窗口变窄时要按优先级折叠，换边时不能丢失面板状态。我们的做法是把摆放规则抽成纯数据的 `PanelPlacement`，视图只负责渲染和命中测试。这样一来，几何逻辑可以在没有窗口的环境里测试，也避免了每个视图各写一套 if-else。

还有导航历史。用户在文件、Diff、会话、搜索之间跳转，期望“后退”回到上一个现场，而不是回到某个固定首页。标签导航历史记录的是“位置”而不是“视图”：文件路径加行号、会话 id 加条目 id、搜索词加结果序号。恢复时按位置重建视图，而不是缓存整个视图树。这个区分很重要——缓存视图会让内存失控，缓存位置则便宜且稳定。

最后是快捷键与命令面板。工作台的复杂度一旦上来，鼠标操作就会变慢；高频动作必须有键盘路径：切换会话、打开搜索、新建标签、关闭标签、跳转文件、显示终端、切换侧栏。命令面板不是装饰，它是复杂功能的可发现性入口。我们尽量让每个命令都有唯一的标识、可搜索的名称和一致的快捷键，而不是散落在各个视图的隐藏手势里。

## 十一、设计系统：把审美变成可执行的规则

一个长时间使用的工具，界面的一致性比惊艳更重要。OhMyAgent 的设计系统不是一组 Figma 文件，而是一组**能被 CI 检查的约束**。

颜色只来自主题令牌：背景、前景、次要文字、三级文字、分隔线、填充、状态色、阴影、图表序列，全部有名字。侧栏与内容区有各自的语义色，且必须不相等；浅色主题的 `#EFEFEF` 与 `#F6F6F7` 只属于“跟随系统”和“Cursor 浅色”，其他主题必须提供自己的取值。原因很简单：把一套浅色值套到深色主题上，对比度会立刻崩塌，而这种问题在开发者的机器上往往看不出来。

字体只来自字号令牌，并且随“界面字号”缩放。正文、次要文字、脚注、代码、时间线各有档位；紧凑控件不允许出现比 `small` 更大的字。图标只用统一图标集，不用 SF Symbol；仅图标控件必须有可访问性标签与悬浮提示；复制按钮只显示图标，成功后短暂变成对勾。按钮有明确的层级：主操作、次操作、文字按钮、破坏性操作、图标按钮，每个区域最多一个主操作。

这些规则听起来琐碎，但它们共同决定了界面“像不像一个东西”。更重要的是，规则必须由机器执行。`Scripts/ui-lint.py` 会扫描源码：硬编码颜色、系统字体、SF Symbol、字面量圆角、装饰性渐变、系统菜单、系统对话框、系统提示，都会让 CI 失败；确需例外时，必须在该行写明原因。人治的规范会随着交付压力逐渐失效，只有 lint 不会疲劳。

主题切换是另一条容易翻车的链路。我们的做法是让视图在 `body` 里读取令牌，令牌读取依赖一个可观察的版本号，主题变化时自动触发刷新；AppKit 桥接的部分（终端、编辑器、托盘）监听主题变更事件，主动重新应用配色。**不要用 `.id(主题)` 强制重建视图**——它看似省事，实际上会丢掉滚动位置、输入焦点和展开状态，是把一个视觉问题变成交互问题。

## 十二、质量守卫：零警告、可重复的演示、诚实的测试

这个工程的 CI 做几件事：本地化扫描、UI 规范扫描、零警告构建、全部测试、plist 与字符串校验。零警告不是洁癖。警告是编译器在说“这里有不确认的地方”，允许警告堆积，等于允许不确认的地方堆积；某一天它们会一起变成 bug。

测试策略是分层而克制的。协议解析、时间线合并、布局计算、路由匹配、主题对比度、字符串插值类型，这些纯逻辑有大量单元测试；UI 测试少而精，优先覆盖最容易回归的交互；端到端则交给演示模式。

演示模式是我们在工程上最满意的设计之一。它创建一个隔离沙盒，生成确定性的演示项目与 Git 仓库，使用脚本化的 Agent 按预设场景产出消息、工具调用、子 Agent、Diff 和终端输出。因为它不依赖真实模型与网络，所以可以无人值守地跑导览、截图、回归。新增一种工具卡或条目类型，必须补一个演示场景；覆盖守卫会检查这件事。这样“这个组件在真实会话里到底长什么样”就不再靠口头描述，而是有一条可执行的路径。

本地化同样是守卫的一部分。界面文案以中文原文为键，英文翻译放在 `en.lproj`，中文资源由脚本生成，禁止手改；扫描脚本会找出遗漏的中文字面量，插值占位符的类型也必须与运行时一致（`Int` 对应 `%lld`，`String` 对应 `%@`）。这类错误在运行时不会崩溃，只会显示成奇怪的格式串，所以必须靠静态检查兜住。

质量守卫的另一半是提交纪律。一次提交只包含一个功能或一个修复，提交信息用中文 Conventional Commits；提交前必须通过完整 CI，未验证的改动不得提交；提交后立即推送。这些规则看起来与代码质量无关，实际上决定了工程能不能长期保持可维护。一个混杂了五个功能的提交，在出问题时无法安全回滚；一个没有经过零警告构建的提交，会把“暂时能跑”变成团队的默认标准。工具可以强制一部分规则，但“小步提交、每步可验证”只能靠纪律。

## 十三、性能：用户感知的是延迟，不是吞吐

我们对性能的关注点只有四个：启动、首字、流式、滚动。

启动阶段，主线程不做任何重活。工作台状态从磁盘恢复，但解析与迁移在后台完成；窗口先出现，内容随后填充。首字延迟靠引擎待命池与连接复用降低；用户按下回车到看到第一个字符之间的空白，是体感上最昂贵的空白。流式阶段靠合批与稳定的条目身份，把刷新频率控制在一帧一次，避免每个 token 都触发一次布局。滚动阶段靠高度缓存、折叠长消息、懒加载代码高亮，保证在几千条消息的会话里依然跟手。

内存方面，标签保活采用 LRU 策略：保留最近使用的若干个会话视图，超出的释放；图片不长期持有原始位图；转录按会话分片存储，不在启动时全量载入。磁盘方面，草稿即时保存，布局与状态轻量持久化，大文件不进 UserDefaults。

所有优化都必须能被测量。我们保留性能输出钩子与性能门槛脚本，避免“感觉快了”这种无法证伪的结论。经验是：**最慢的地方往往不是算法，而是主线程上的同步 I/O、富文本布局和图片解码**。先消灭这三类，再谈更深的优化。

还有一个容易被忽略的维度是“切换成本”。用户频繁在会话、文件、Diff、终端之间跳转，每一次切换都应该在一两帧内完成。缓存视图、预解析相邻文件、保留滚动锚点、延迟加载不可见内容，都是为了让切换没有存在感。与之相对，启动时一次性恢复所有标签、预读所有文件、重建所有高亮，是最常见的“优化变慢”案例：它把成本从用户真正需要的那一刻，提前到了应用启动的那一刻。性能优化的本质不是让所有事情变快，而是把成本挪到用户不在意的地方。

## 十四、安全：能力越大，边界越要清楚

一个能读写文件、执行命令、访问网络的桌面 Agent，本质上是一个被授予了用户权限的程序。安全设计不能建立在“模型不会做坏事”之上。

第一，凭据不落地。不读取 Keychain 里的 OAuth 令牌，官方 CLI 使用自己的凭据；代理内存里持有厂商密钥，子进程只拿到路由令牌；日志脱敏，协议载荷默认不记录。

第二，权限显式化。工具调用必须经过审批，审批界面展示真实参数与真实命令；支持“本次允许”和“始终允许”，但后者应当是用户明确的选择，而不是默认值；拒绝要有结构化反馈。

第三，路径有边界。文件操作限制在工作区与用户明确授权的目录内；对 `..`、符号链接、大小写不敏感文件系统等细节做规范化后再判断；不要把“拼接字符串后前缀匹配”当成路径校验。

第四，网络有边界。本地网关只绑定回环地址，校验 Host，令牌放在路径中并按会话撤销；不要让网关变成局域网可访问的开放代理。

第五，输入皆不可信。模型输出、工具输出、文件内容、网页内容都可能携带诱导性指令。宿主必须区分“数据”和“指令”，在执行任何副作用前做策略判断。这是 Agent 产品最容易被低估的攻击面。

## 十五、反模式：那些我们刻意不做的事

回头看，这个工程里很多决定是“不做”而不是“做”。

**不把 Agent 当聊天。** 聊天框只需要文本，工作台需要状态、工具、权限、Diff、终端和恢复。把前者套到后者上，会在第二个功能点就开始别扭。

**不在视图里做 I/O。** 视图的 `body` 应该是纯函数。任何磁盘、网络、子进程、解析，都应该在进入视图之前完成。违反这条的代码在演示时很快，在真实会话里一定会抖。

**不用 `.id()` 解决刷新。** 主题变了就重建视图，列表变了就重建列表，最终会丢掉所有用户状态。正确的方法是让数据变化驱动最小范围的更新。

**不靠人工守规范。** 颜色、字体、圆角、图标、菜单、对话框、本地化，全部交给 lint 与测试。规范只有两种结局：被机器执行，或者被时间腐蚀。

**不把多个功能混进一次提交。** 一次提交只做一件事，提交信息用中文 Conventional Commits。这不是仪式，而是为了让回滚、定位、审查都保持廉价。

**不追求“全平台”。** 对一个深度依赖 macOS 交互与系统能力的工具，跨平台意味着把每个平台都做成第二名。我们宁愿在一个平台上做到没有替代品。

**不把测试写成 happy path 展览。** 真正会出 bug 的地方是：流式中途取消、工具调用并发、会话快速切换、进程崩溃、权限超时、主题切换、窗口失焦。测试应该往这些地方扎。

## 十六、结语：原生的意义是尊重延迟

做这个产品的过程中，我越来越觉得，“原生”这个词的真正含义不是某种技术栈，而是一种对延迟和确定性的尊重。

用户按下回车，应该在下一帧看到反馈；用户输入中文，候选词不应该被吞掉；用户往上翻历史，视角不应该被拽回底部；用户拒绝一次工具调用，Agent 应该立刻知道；用户切换主题，滚动位置和输入焦点应该还在原地。这些事情单拎出来都很小，但它们叠加起来，就是“这个工具能不能被信任”。

Agent 的能力会越来越强，模型会越来越快，协议会越来越复杂。但工作台的价值不会因此消失，反而会更高：当 Agent 能做的事情越来越多，人需要的不是一个更长的聊天记录，而是一个能看清它在做什么、能随时接管、能在出问题时回退的现场。原生桌面应用恰好擅长构建这样的现场——它有真实的窗口、真实的焦点、真实的文件系统、真实的进程，以及真实的延迟。

OhMyAgent 还有很多没做完的事：更强的多 Agent 协作、更细的上下文治理、更自然的语音与手势、更完善的自动化。但方向是清楚的：把复杂的 Agent 能力，收进一个安静、快速、可预期的桌面壳里。用户不需要知道 JSON-RPC、SSE、actor 隔离和主题令牌，他们只需要知道——按下回车，事情会开始；事情做完，他们能看懂；出了问题，他们能接住。

这大概就是一个 Agent 工作台应该有的样子，也是我们愿意为每一毫秒较真的原因。
