# 内存与 CPU 占用优化方案

> @author ixxxxoooo
> 日期:2026-10-19
> 范围:Agent 进程模型、预热池、应用内轮询与缓存。只做排查与方案,尚未改代码。

## 1. 结论

- 现在每个会话标签常驻一个 Node 适配器和一个 `claude` CLI,实测空闲时约 **380 MB/标签**。只有关闭标签、移除项目或退出应用时才回收。
- "改成一个 Agent 进程"**只能省掉 Node 外壳(约 100 MB/会话)**。Claude Agent SDK 的设计是一个会话对应一个 `claude` CLI 子进程(适配器源码注释原话:`query()` spawns the CLI at once),这部分约 265 MB/会话,无论适配器有几个都省不掉。
- 真正的杠杆是**同时存活的 CLI 数量**。推荐方案 D:共享适配器 + 会话级休眠 + 活跃上限。10 个标签、2~3 个活跃时,内存从约 3.8 GB 降到约 0.9 GB。
- 应用内另有几处不必要的 CPU 消耗:GitDiff 每 2 秒拉起一个 `git` 子进程;自绘滚动条默认每 1.5 秒在主线程遍历整个视图树;资源指标每 30 秒在主线程全量遍历所有时间线。这些修起来成本低。

## 2. 实测数据

测试方法:直接启动 `Vendor/acp` 里的适配器,通过 ACP 依次执行 `initialize` 和 `session/new`/`session/resume`,**不发提示词**,用 `ps` 统计进程树的 RSS。机器为 macOS 27,`claude` 2.1.303,适配器 `claude-agent-acp` 0.91.0。

| 场景 | 进程数 | 合计 RSS |
|---|---|---|
| 只有适配器 | 1(node) | 115 MB |
| 1 个会话 | node + 1×claude | 383 MB |
| 2 个会话 | node + 2×claude | 627 MB |
| 3 个会话 | node + 3×claude | 893 MB |

- Node 适配器约 100–115 MB。每个空闲的 `claude` CLI 约 265 MB,实际使用后还会增长。本机一个跑了 11 分钟的 Claude Code 进程是 525 MB。
- `session/new` 耗时约 1.3 秒。
- `session/resume`(唤醒已有会话,不回放历史):2.1 MB 的历史 **2.1 秒**,小会话 1.5 秒。唤醒后的内存和新建会话相同。
- 每个 `claude` CLI 会各自再拉起用户配置的全部 **stdio** MCP 服务器。本机目前只配了 http 类型的 MCP,所以没有额外子进程。但只要配一个 stdio MCP(例如 chrome-devtools-mcp,一套约 3 个进程、400 MB),就会再乘以会话数。

## 3. 现状问题清单

### P0:进程常驻且没有回收
1. **一个会话标签一套进程,一直常驻**。`SessionModel` 自己持有 `AgentSupervisor`(`SessionModel.swift:341`、`:427`)。回收只发生在 `reapConversations`(标签关闭)、移除项目和退出应用。切换项目不会回收其他项目的会话。会话标签不参与 LRU(`TabKeepAlive.swift:59`)。
2. **预热池不受总量约束**。`EngineWarmPool.capacity = 4`。打开引擎选择器会一次预热最多 4 个其他引擎(`planForPicker`),这些待命进程要等切换项目才回收。最坏情况多出约 1.5 GB。

### P1:重复开销与无谓的子进程
3. **每个会话一个 Node 适配器**,每多一个会话就重复约 100 MB 的运行时开销。
4. **GitDiffView 处于活动状态时每 2 秒执行一次 `git diff`**(`GitDiffView.swift:43`),也就是每 2 秒拉起一个子进程。工作区已经有 FSEvents(`WorkspaceWatcher`),应改为事件驱动。
5. **自绘滚动条默认是 `.custom`,每 1.5 秒在主线程递归遍历整个窗口的视图树**(`ScrollbarPolicy.swift:89`),视图越多越慢。

### P2:小的持续开销
6. 文件标签每秒 `stat` 一次检查外部修改(`TabContentView.swift:198`)。单次很便宜,但可以并入 FSEvents。
7. `PerfGauges` 每 30 秒在主线程遍历**所有会话的所有时间线条目**,并计算 `utf8.count`(`PerfGauges.swift:34`)。时间线越大,越容易造成周期性卡顿。
8. 时间线条目和图片附件(单张上限 5 MB)都常驻内存。休眠的会话以后也会保留这部分内存。
9. `ACPClient.events` 使用 `.unbounded` 缓冲(`ACPClient.swift:222`),消费变慢时会无限堆积。

### 已经做对的部分(保持不变)
- 启动时会话按需恢复(`pendingRestores`,标签首次显示才建会话)。
- LSP 懒启动、按种类和根目录复用、闲置 180 秒回收、有数量上限(`LSPManager`)。
- 浏览器标签上限 8 个,按 LRU 淘汰。Markdown、高亮、Mermaid、图片缓存都是有上限的 `NSCache`。
- 标题生成、提示词优化走 HTTP(`TitleGenerator.generate`),不另起进程。Bridge 是进程内 HTTP(挂在 `LocalGateway` 上)。
- Git 圆点轮询有退避,且只在应用处于前台时进行(`RightPaneView.pollGitBadge`)。
- 不可见标签的 `ActiveTimeline` 降到 600 秒才刷新一次。

## 4. 进程模型方案对比

以"打开 10 个会话标签,其中 2~3 个在用"为例(按空闲内存估算,不含预热池):

| 方案 | 做法 | 内存估算 | 唤醒延迟 | 改动量 | 主要风险 |
|---|---|---|---|---|---|
| A 现状 | 每会话一套 node + claude | 10×380 ≈ **3.8 GB** | 0 | 无 | 内存随标签数线性增长 |
| B 会话休眠 | 每会话仍独立;闲置或超过上限的会话结束进程,用到时 `session/resume` | 3×380 ≈ **1.1 GB** | 1.5–2 秒(可预唤醒) | 小 | 休眠会丢掉 CLI 内的后台任务,需要守卫 |
| C 共享适配器 | 每种"引擎配置"一个 node,会话各自一个 claude | 100+10×265 ≈ **2.75 GB** | 0 | 中 | 适配器崩溃会影响所有会话;回调必须按会话路由 |
| **D = B + C(推荐)** | 共享适配器 + `session/close` 休眠 + 活跃上限 LRU | 100+3×265 ≈ **0.9 GB** | 1.5–2 秒(可预唤醒) | 中 | 同 B、C 的风险,分阶段上线 |
| E 单个 claude 跑多会话 | 不用 Agent SDK,自己实现 Agent 循环 | 最低 | 0 | 极大 | 相当于重写 Claude Code,违背"接管本机 claude"的定位,**不可行** |

各方案的优缺点:

- **A**:实现最简单,会话之间完全隔离,切换没有延迟。代价是内存随标签数线性增长,不用的会话也一直占着。
- **B**:收益最大、改动最小,完全复用现有的 `resumeSession` 路径(`refreshModelMapping` 已经实现过"保留时间线、重建 CLI 会话",见 `SessionModel.swift:1632`)。缺点是唤醒有 1.5–2 秒冷启动,而且每个活跃会话仍然各带一个 Node。
- **C**:每会话省约 100 MB,新建会话少一次 Node 启动(约 0.3 秒)。缺点是故障域变大,并且要把回调从"每连接一个代理"改成"按 sessionId 路由"。**单独做 C 的收益不如单独做 B**。
- **D**:内存最低,而且是可以控制的上限,不会随标签数增长;结构上也和 Zed 等 ACP 客户端一致。缺点是两部分改动叠加,必须分阶段做,并保留开关以便回退。

## 5. 推荐方案 D 的设计

### 5.1 会话驻留策略(纯模型,放在 WorkbenchKit,带测试)
`SessionResidencyPolicy` 输入所有会话的状态,输出应该休眠的会话列表:
- **不能休眠**的情况:运行中(`isRunning`);有待处理的权限或提问;有未退出的后台终端(`terminals`,包括 Claude Code 报告的外部后台任务);子代理运行中;当前可见的会话标签;连接中或正在回放。
- **休眠触发**:闲置超过 T(默认 10 分钟,可设为"从不");或活跃数超过上限 K(默认 3,按 LRU);或系统内存压力(`DispatchSource.makeMemoryPressureSource`)为 warning/critical 时降到 1。
- 预热池计入同一预算:待命会话优先被回收;内存压力下停止预热;`smart` 模式保留,`planForPicker` 的上限从 4 降到 2。

### 5.2 SessionModel 增加"休眠"阶段
- `hibernate()`:结束 CLI 会话,保留 `timeline`、`sessionId`(另存为 `dormantSessionId`)、草稿、配置项和标题。阶段一直接调用现有的 `shutdownProcess()`;阶段二改为对共享连接发 `session/close`。
- `wake()`:用 `session/resume` 恢复(不回放,时间线已经在内存里)。恢复失败时提示,并走 `startFreshSession`(和映射刷新的兜底一致)。
- **预唤醒**:输入框获得焦点或开始输入时就开始唤醒。用户输入通常超过 2 秒,大多数情况下感觉不到延迟。唤醒完成前按发送,直接放进现有的排队消息机制。
- 界面:会话状态点增加"休眠"态(空心、灰色),悬浮提示"已休眠,发送消息时自动恢复"。

### 5.3 共享适配器 `AgentHub`(AgentHost / ChatKit)
- 池键:`descriptor.id` + 进程级 env 摘要 + 连接能力(fs/terminal/扩展)。会因会话而异的配置必须全部通过 `_meta` 传(适配器已支持按会话合并 `_meta.claudeCode.options.env`,见 `acp-agent.js` 中 `createSession` 的 env 合并逻辑)。
- 引用计数:`acquire` 拿到连接;`release` 后引用计数归零并闲置 60 秒才结束 Node。
- **路由**:`ClientEvent` 按 `sessionId` 分发到各个 `SessionModel`;`requestPermission`、`readTextFile`、`writeTextFile`、`createTerminal`、`elicit` 按参数里的 `sessionId` 路由;`terminal/*` 只带 `terminalId`,需要维护 `terminalId → sessionId` 映射。找不到会话的请求返回错误并记日志,**绝不能投递给其他会话**。
- 崩溃恢复:Node 退出后按指数退避重启,对所有活跃会话依次 `session/resume`;正在运行的轮次标记为中断并提示。
- 开关:`agent.sharedAdapter`,默认关闭,验证稳定后再默认开启;出问题可以立即回退到每会话独立进程。

### 5.4 CPU 修复
- GitDiffView:改为订阅 `WorkspaceWatcher` 的批量事件(防抖 300 ms 后执行一次 `git diff`),去掉 2 秒轮询。
- ScrollbarPolicy:去掉 1.5 秒巡检,改为在标签切换、面板显示、窗口布局变化时执行一次,或者在 `NSScrollView` 子类或安装点里自行处理。
- 文件外部修改:并入 `WorkspaceWatcher`,只在活动标签收到相应路径的事件时 `stat`。
- PerfGauges:`TimelineStore` 增量维护条目数、字节数、图片字节数等计数器,采样时只读计数器。
- `ACPClient.events`:保持 `unbounded`,避免丢事件破坏协议;增加积压量指标,超过阈值时报警告日志。

### 5.5 休眠会话的内存(可选,最后做)
- 休眠会话的图片附件只保留缩略图,原图转存到 `AppEnv.supportDirectory/cache/attachments`,需要时再读回。
- 不卸载时间线文本:文本占用通常只有几 MB,卸载后再回放代价高。

## 6. 分阶段实施

| 阶段 | 内容 | 收益 | 风险 |
|---|---|---|---|
| 0 | 基线:补充"存活 CLI 数、休眠数、各子进程内存"指标,接入 `ResourceSampler` | 有前后对比数据 | 无 |
| 1 | 会话休眠(方案 B)+ 预热池计入预算 + 内存压力响应 | 大部分内存收益 | 低 |
| 2 | CPU 修复(5.4) | 降低空闲时的 CPU 与卡顿 | 低 |
| 3 | 共享适配器 `AgentHub` + 路由 + 崩溃恢复,带开关(方案 D) | 每会话再省约 100 MB,新建会话更快 | 中 |
| 4 | 休眠会话图片转存(5.5) | 图片多时有明显收益 | 低 |

每个阶段单独提交,带 Swift Testing 测试:驻留策略、路由表、池引用计数都是纯模型,可以直接测;演示模式要补"休眠/唤醒"场景。
