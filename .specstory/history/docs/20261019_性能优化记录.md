## 1. 流式渲染

背景:与 `~/baocode`(外部参考,仓库外的 Flutter 项目)对比后,判断卡顿集中在流式回复时主线程的文字排版、滚动跟随的高频回调与遮罩离屏渲染。

### 1.1 度量方法

- **流式渲染微基准**:`Tests/OhMyAgentAppTests/StreamingRenderBenchTests.swift`。把约 20KB 的助手回复(标题、段落、列表、行内代码、引用交替,无围栏代码块)按 48 字一批追加,每批执行「Markdown 增量解析 → 文字段渲染 → 排版测量」,统计每批主线程耗时。运行 `Scripts/test.sh --filter StreamingRenderBench`,结果在标准错误的 `[基准]` 行。
- **UI 交互基准**:`Scripts/perf-ui.sh interact --build --sessions 6`。卡顿取证:`OMA_HITCH_SAMPLE=1`(`HitchStackSampler`,日志「卡顿栈」)。

### 1.2 基线(优化前)

| 项 | 数据 |
|---|---|
| 20KB 流式,全程每批 | 216 批,中位 13.6ms,P95 26.7ms,最大 42.7ms,合计 3051ms |
| 20KB 流式,最后 25% | 中位 24.5ms,P95 27.6ms(已超过一帧 16.7ms) |
| UI:冷打开时间线挂载 | 41ms |
| UI:标签热切换 | 中位 24ms,P95 87ms |
| UI:启动前主线程卡顿 | 5 次,最长 260ms |

结论:每批耗时随文本长度线性增长(前 75% 约 8ms,后 25% 约 24ms),原因是每批都对整段文字重建富文本并整体重排(`MarkdownTextRunBuilder.build` 整段重建 + `setAttributedString` + `ensureLayout`)。

### 1.3 优化记录

| 项 | 优化前 | 优化后 | 提交 |
|---|---|---|---|
| Markdown 文字段流式,每批中位(20KB,debug) | 13.6ms | 0.78ms | `aeb9030` |
| 同上,最后 25% 中位 | 24.5ms | 1.08ms | `aeb9030` |
| 6KB 代码块流式高亮,每批中位 | 2.0ms | 0.16ms | `88df8d7` |
| 同上,最后 25% | 3.5ms | 0.24ms | `88df8d7` |
| 事件合并窗口 | 固定 50ms | 16ms 起,按主线程处理耗时(EMA×2)自适应,上限 80ms | `24016b4` |
| 会话流滚动区离屏渲染 | 整体 `.mask` | 上下两条渐变覆盖层 | `f387605` |
| 贴底跟随 `scrollTo` | 每个事件一次 | 每帧至多一次 | `e3ac243` |
| 时间线挂载量 | 全部回合 | 最近 40 轮 + 「显示更早的 N 轮对话」 | `59fa51c` |
| Mermaid 预览仓库 | 无上限 | 64 条 LRU | `08af8d6` |
| 流积压 | 只记峰值 | 超过 5000 条记警告,回落一半后可再次告警 | `e6fc77f` |

原理:按块缓存 `NSAttributedString`,只重建最后一块,并用 `replaceCharacters` 只替换尾部,每批成本与已有文本长度基本无关。

UI 交互基准(release,`perf-ui.sh interact --sessions 6`)复测:冷打开挂载 41ms、热切换中位 24ms/P95 87ms、启动前卡顿 5~6 次最长 260ms,与基线一致。该场景不含流式输出,本轮优化针对流式与长会话,不变是预期结果而非回退。

### 1.4 取舍(按测量结果)

| 候选 | 结论 | 依据 |
|---|---|---|
| 拆分 `SessionModel`(约 2000+ 行) | 暂不拆 | 热点在渲染链而非模型逻辑;`handle(batch)` 已被自适应窗口兜住;拆分触及几乎所有会话测试,收益不可测 |
| AppKit 虚拟列表替换 `LazyVStack` | 暂不做 | 最近 40 轮的窗口化已使挂载量有界。若单轮内工具卡超过数百个再评估 |
| 启动/回放分帧 | 暂不做 | 启动前卡顿来自一次性加载与引擎拉起,与会话渲染无关;如需继续,优先把 `WorkbenchStore.load` 改异步并用 `OMA_HITCH_SAMPLE=1` 取栈 |
| 直连 stream-json / 共享适配器 | 不做 | 见 `20261019_直连stream-json与共享适配器评估.md` |

遗留可选项:对 release 补一个流式场景的 UI 基准(已有 `perf-ui.sh stream` 只记录不设门槛);窗口化后为「显示更早」补键盘快捷键。

## 3. 侧栏开关与会话切换

现象:开关左右侧栏掉帧;整页偶发卡顿;切换/冷打开会话偶发 1~2 秒冻结。数据来源:`~/Library/Logs/OhMyAgent[-Dev]` 的 `侧栏切换`/`标签切换`/`时间线挂载`/`主线程卡顿`/`资源采样`、`/usr/bin/sample` 栈采样、演示模式基准 `Scripts/perf-ui.sh`。

### 3.1 根因与修复

| 问题 | 根因 | 修复 | 位置 |
| --- | --- | --- | --- |
| 侧栏开关掉帧 | 动画挂在整个 HStack 的 `.animation(value:)` 上,中栏宽度逐帧变化,会话流/时间线每帧重排 | 动画只绑在面板自身的 `AnyTransition.animation(_:)`,中栏一次性到位;滑出的面板 `zIndex(1)` 盖在已变宽的中栏上 | `WorkbenchView.swift` |

## 4. 内存与 CPU 占用

范围:Agent 进程模型、预热池、应用内轮询与缓存。**状态:阶段 0~2 已完成,阶段 3(共享适配器)评估后不做,阶段 4 未做。**

### 4.1 进程占用(进程模型事实,其他文档引用此节)

- 每个会话一套进程:Node 适配器(`claude-agent-acp`)+ `claude` CLI。Claude Agent SDK 的设计是一个会话对应一个 `claude` CLI 子进程(适配器源码注释:`query()` spawns the CLI at once),因此「合并成一个 Agent 进程」只能省掉 Node 外壳(约 100 MB/会话),约 265 MB/会话的 CLI 无论适配器有几个都省不掉。
- 真正的杠杆是同时存活的 CLI 数量,所以采用「会话休眠 + 驻留上限」(§4.4);共享适配器的评估与否决见 `20261019_直连stream-json与共享适配器评估.md`。

实测方法:直接启动 `Vendor/acp` 里的适配器,通过 ACP 依次 `initialize` 和 `session/new`/`session/resume`,不发提示词,用 `ps` 统计进程树 RSS。macOS 27,`claude` 2.1.303,适配器 `claude-agent-acp` 0.91.0。

| 场景 | 进程数 | 合计 RSS |
|---|---|---|
| 只有适配器 | 1(node) | 115 MB |
| 1 个会话 | node + 1×claude | 383 MB |
| 2 个会话 | node + 2×claude | 627 MB |
| 3 个会话 | node + 3×claude | 893 MB |

- Node 适配器约 100–115 MB;空闲 `claude` CLI 约 265 MB,使用后还会增长(本机一个跑了 11 分钟的 Claude Code 进程 525 MB)。
- `session/new` 约 1.3 秒;`session/resume`(不回放历史):2.1 MB 历史 2.1 秒,小会话 1.5 秒,唤醒后内存与新建会话相同。
- 每个 `claude` CLI 会各自再拉起用户配置的全部 stdio MCP 服务器(例如 chrome-devtools-mcp 一套约 3 个进程、400 MB),会再乘以会话数;http 类型 MCP 不产生子进程。
- 以「10 个会话标签、2~3 个在用」估算:全部常驻约 10×380 ≈ 3.8 GB;休眠到 3 个存活约 3×380 ≈ 1.1 GB。
- 其他进程:LSP 懒启动、按种类与根目录复用、闲置 180 秒回收、有数量上限(`LSPManager`);标题生成与提示词优化走 HTTP(`TitleGenerator.generate`);Bridge 是进程内 HTTP(挂在 `LocalGateway`);浏览器标签上限 8 个按 LRU 淘汰。
- 本次测试没有测量应用本体(Swift 进程)在多标签下的内存(待补)。

休眠规则(`SessionResidencyPolicy` + `ClientPrefs`):
- 不休眠:运行中;有待处理权限/提问;有未退出的后台终端或 Agent 进程下仍挂着 shell 命令;子代理运行中;正显示在标签里的会话;连接中或回放中。
- 触发:闲置超过 10 分钟(`idleHibernateMinutes`,范围 0~240,0 为从不)或存活数超过 3(`maxLiveSessions`,范围 0~32,0 不限,按最久未用优先);系统内存压力 warning/critical 时收紧为闲置 1 分钟、只留 1 个(`underPressure`,`DispatchSource.makeMemoryPressureSource`)。设置页有「启用会话休眠」与「内存紧张时提前休眠」开关。
- 唤醒:`wake()` 用 `session/resume` 恢复(时间线已在内存,不回放);输入或发送时自动触发,唤醒完成前的发送进入排队;接回与新建都失败则进入失败态(可重连)。
- 预热池:待命引擎优先回收;`smart` 模式保留。
