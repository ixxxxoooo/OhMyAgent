# 流式渲染性能基线与优化记录

> @author ixxxxoooo
> 日期:2026-10-19
> 背景:与 `~/baocode`(Flutter)对比后,判断 OhMyAgent 的卡顿集中在**流式回复时主线程的文字排版**、滚动跟随的高频回调与遮罩离屏渲染。本文记录基线与每项优化前后的数据。

## 1. 度量方法

- **流式渲染微基准**:`Tests/OhMyAgentAppTests/StreamingRenderBenchTests.swift`。把一条约 20KB 的助手回复(标题、段落、列表、行内代码、引用交替,无围栏代码块,即一整段文字)按 48 字一批追加,每批执行「Markdown 增量解析 → 文字段渲染 → 排版测量」,统计每批主线程耗时。运行:`Scripts/test.sh --filter StreamingRenderBench`,结果在标准错误的 `[基准]` 行。数据为 **debug 构建**,绝对值偏大,但相对变化有效(耗时主要在 TextKit / AttributedString 等系统代码里)。
- **UI 交互基准**:`Scripts/perf-ui.sh interact --build --sessions 6`(演示模式,release 构建)。
- 卡顿取证:`OMA_HITCH_SAMPLE=1`(`HitchStackSampler`,日志「卡顿栈」)。

## 2. 基线(优化前)

| 项 | 数据 |
|---|---|
| 20KB 流式,全程每批 | 216 批,中位 13.6ms,P95 26.7ms,最大 42.7ms,合计 3051ms |
| 20KB 流式,最后 25% | 中位 24.5ms,P95 27.6ms(已超过一帧 16.7ms) |
| UI:冷打开时间线挂载 | 41ms |
| UI:标签热切换 | 中位 24ms,P95 87ms |
| UI:启动前主线程卡顿 | 5 次,最长 260ms |

**结论**:每批耗时随文本长度**线性增长**(前 75% 约 8ms → 后 25% 约 24ms),说明每批都对整段文字重建富文本并整体重排。这与代码阅读的判断一致(`MarkdownTextRunBuilder.build` 整段重建 + `setAttributedString` + `ensureLayout`)。

## 3. 优化记录

| 项 | 优化前 | 优化后 | 提交 |
|---|---|---|---|
| Markdown 文字段流式,每批中位(20KB,debug) | 13.6ms | 0.78ms | `aeb9030` |
| 同上,最后 25% 中位 | 24.5ms | 1.08ms | `aeb9030` |
| 6KB 代码块流式高亮,每批中位 | 2.0ms | 0.16ms | `88df8d7` |
| 同上,最后 25% | 3.5ms | 0.24ms | `88df8d7` |
| 事件合并窗口 | 固定 50ms | 16ms 起,按主线程处理耗时(EMA×2)自适应,上限 80ms | `24016b4` |
| 会话流滚动区离屏渲染 | 整体 `.mask` | 上下两条渐变覆盖层 | `f387605` |
| 贴底跟随 `scrollTo` | 每个事件一次 | 每帧至多一次 | `e3ac243` |
| 时间线挂载量 | 全部回合 | 最近 40 轮 + 「显示更早的 N 轮对话」 | `59fa51c` |
| Mermaid 预览仓库 | 无上限 | 64 条 LRU | `08af8d6` |
| 流积压 | 只记峰值 | 超过 5000 条记警告,回落一半后可再次告警 | `e6fc77f` |
| 编辑器 Agent 标记 | 任一会话改动都重新赋值 | 结果不变不赋值 | `2a756f7` |

**原理**:优化前每批都对整段文字重建富文本并 `setAttributedString` 整体重排,耗时随长度线性增长;现在按块缓存 `NSAttributedString`,只重建最后一块,并用 `replaceCharacters` 只替换尾部,每批成本与已有文本长度基本无关。

**UI 交互基准(release,`perf-ui.sh interact --sessions 6`)复测**:冷打开挂载 41ms、标签热切换中位 24ms/P95 87ms、启动前卡顿 5~6 次最长 260ms,与基线一致。该场景(演示模式切会话、开关侧栏)**不含流式输出**,本轮优化针对流式与长会话,因此此场景不变是预期结果,并非回退。

## 4. 阶段 4 的取舍(按测量结果)

| 候选 | 结论 | 依据 |
|---|---|---|
| 拆分 `SessionModel`(约 2000+ 行) | **暂不拆** | 当前卡顿热点已定位在渲染链而非模型逻辑;`handle(batch)` 的耗时已被自适应窗口兜住;拆分会触及几乎所有会话相关测试,收益不可测 |
| AppKit 虚拟列表替换 `LazyVStack` | **暂不做** | 窗口化(最近 40 轮)已把挂载量封顶;`LazyVStack` 不回收视图,但 40 轮上限使内存与布局成本有界。若后续单轮内工具卡超过数百个再评估 |
| 启动/回放分帧 | **暂不做** | 启动前卡顿 5~6 次最长 260ms 来自一次性加载与引擎拉起,与会话渲染无关;历史回放事件已走合批与窗口化。如需继续,优先把 `WorkbenchStore.load` 改异步并用 `OMA_HITCH_SAMPLE=1` 取栈确认 |
| 直连 stream-json / 共享适配器 | 不做,见 `20261019_直连stream-json与共享适配器评估.md` | |

**遗留可选项**:① 对 release 构建补一个流式场景的 UI 基准(演示场景里持续喂 `agent_message_chunk`),把渲染优化也纳入 `perf-ui.sh` 的门槛;② 窗口化后为「显示更早」补键盘快捷键。
