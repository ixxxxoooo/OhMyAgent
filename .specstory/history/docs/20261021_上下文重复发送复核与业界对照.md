# 上下文重复发送复核(原生适配器)与业界对照

> @author ixxxxoooo · 2026-10-21 · 复核 `20261020_Token消耗与上下文重复发送分析.md`(当时还是 Node 适配器),现用原生 Swift 适配器重测。

## 结论
1. **客户端没有重复发送**:`SessionModel.promptBlocks` 只构造本轮的文本/图片/文件链接;`ClaudeSession.prompt` 经 `query.sendUser` 只把这一条写入常驻 `claude` 进程(stream-json),历史由 `claude` 进程自己持有。追加系统提示(`appendPrompt`、图表提示等)在建会话时通过 `_meta` 设置一次,不是每轮追加。
2. **每轮整包重发历史是模型 API 的协议特性**(无状态),由 Claude Code 完成,靠提示缓存降价:缓存读取约 0.1× 价,缓存写入约 1.25× 价(倍率来自第三方网关文档转述,以 Anthropic 官方定价页为准)。
3. **疑点(已定位并修复,见文末「排查」)**:真实测试里第 1、2 轮各写入约 1.5 万 token 缓存(第 2 轮本应只新增几百),第 3 轮起才稳定在每轮只写 14 token。昨天 `claude -p --resume` 的实测没有这个现象。可能与首轮后工具列表变化(MCP 工具按需加载)或会话预热有关,尚未定位。影响:每个新会话的前两轮多付一次约 1.5 万 token 的 1.25× 写入。

## 业界做法对照
| 做法 | 来源 | 本项目 |
|---|---|---|
| 稳定前缀:system、tools 在前且不变,缓存按 tools→system→messages 顺序匹配 | Anthropic 提示缓存文档、Manus | 不改写 system/tools,已有 4 个断点 |
| 默认 TTL 5 分钟,命中即续期;可选 1 小时 | Anthropic 文档 | 间隔超 5 分钟会整段重写,属正常 |
| 最多 4 个断点,前缀需 ≥~1024 token | Anthropic 文档(网关转述) | 满足 |
| 序列化确定性(JSON key 顺序)、不改历史动作/观察 | Manus | 代理转换使用 `.sortedKeys` |
| 压缩要有理由:有缓存时保留完整历史往往更便宜、召回更好 | 业界评测转述 | 沿用 Claude Code 自动压缩,阈值可配 |
| 长会话用工具结果裁剪、子 Agent、新开话题 | 业界博客 | 建议无关话题新开会话 |

## 排查:第 2 轮多写 1.5 万 token 缓存(2026-10-21,已修复 8b44f40)

方法:本机透传代理(只记录请求结构指纹与 usage,不记录请求头/凭据)接住真实 `claude` → api.anthropic.com,逐请求对比 tools/system/每条消息的哈希,算出与上一次请求的「公共消息前缀」。用户级已配置 5 个远程 MCP 服务;会话另挂一个本地 stdio MCP(`kv_get`/`word_count`)。

### 各组结果(按轮汇总,单位 token)
**A 组**:`ENABLE_TOOL_SEARCH=true`(应用默认),8 轮,含 MCP 调用、读文件、Bash
| 轮 | 内容 | 新输入 | 缓存写入 | 缓存读取 | 输出 |
|---|---|---|---|---|---|
| 1 | 打招呼 | 2 | 26514 | 0 | 92 |
| 2 | MCP kv_get | 10 | 409 | 80002 | 185 |
| 3 | 读 README | 6 | 213 | 53906 | 141 |
| 4 | Bash ls | 6 | 151 | 54333 | 100 |
| 5 | MCP kv_get + word_count | 10 | 461 | 82293 | 341 |
| 6 | 3+4 | 4 | 138 | 27748 | 3 |
| 7 | 5+6 | 4 | 16 | 27886 | 3 |
| 8 | 7+8 | 4 | 16 | 27902 | 3 |

带工具的轮次是多次请求(每步工具调用一次请求)之和,所以读取约为 2~3 倍前缀。全部请求的消息前缀都完整复用;按需加载使 tools 从 11 增至 13 个,缓存仍完整命中。**B 组**(不设变量)结果与 A 几乎一致:当前 `claude` 默认已按需加载 MCP 工具。

**C 组(复现)**:不挂本地 MCP、建会话后立刻发,6 轮 `n+n`
| 轮 | 新输入 | 缓存写入 | 缓存读取 |
|---|---|---|---|
| 1 | 2 | 16646 | 8186 |
| 2 | 2 | **15860** | 10764 |
| 3 | 4 | 1792 | 24845 |
| 4~6 | 4 | 14 | 26637~26665 |

### 根因
当前 `claude` 把环境说明、CLAUDE.md 等放进 messages 里一条 `role: system` 消息(约 31KB)。远程 MCP 在第 1 轮发出**之后**才连上,第 2 轮请求追加了「工具可用」系统消息(含 `tool_addition` 块),同时那条上下文消息从「块数组」被改成「纯字符串」重发——文字相同但字节不同,缓存从这条起全部失效。建会话后等 10 秒再发(C3 组),第 2 轮写入仅 23,验证了时序假设。属 `claude` 自身行为,我们只能规避。

### 修复
`ClaudeSession+McpReady.swift`:会话就绪(`boot` 末尾)即后台轮询 `mcp_status`,直到没有 `pending` 服务器(上限 5 秒);首条 `session/prompt` 发出前等待该任务。应用里会话通常已预热,用户打字期间就完成了,几乎不增加延迟。

**D 组(修复后,同 C 条件)**:第 2 轮写入 **35**(原 15860),之后每轮 16;每次请求消息前缀完整复用。

### 其他观察(未改)
- 每个会话有一次用**主模型**发出的约 1.2k token 无缓存小请求(无工具,标题/摘要类),费用很小。
- 基础前缀约 2.65 万 token(系统提示 + 内置工具 + 上下文消息),第 1 轮必然写入一次;跨会话可复用约 8k(tools + 前两段 system)。

复现脚本放在会话草稿目录(透传代理 `proxy.py`、本地 MCP `mcp.py`、驱动 `drive.py`、分析 `ana.py`),未入库:代理会转发真实凭据,只适合本机手动排查。

## 复核二:真实会话记录统计与可优化点(2026-10-21)

数据源:`~/.claude/projects` 下 10 月的会话记录(每条助手消息带当次请求 usage,按 `message.id` 去重;`entrypoint`:`sdk-cli`=原生适配器,`sdk-ts`=旧 Node 适配器,`cli`=终端)。

| 入口 | 模型 | 请求数 | 无缓存输入 | 缓存写 | 缓存读 |
|---|---|---|---|---|---|
| sdk-cli | claude-opus-5-5 主会话 | 695 | 1,468 | 6,368,932 | 156,609,159 |
| sdk-cli | claude-opus-5-5 子代理 | 322 | 2,861 | 2,312,329 | 70,805,782 |
| sdk-cli | claude-sonnet-5-5 | 1271 | 532,671 | 11,761,296 | 279,217,521 |
| sdk-cli | deepseek-v4.1-flash(ZYB) | 193 | 10,180,212 | 0 | 2,020,480 |
| sdk-ts | gpt-6-astra(ZYB) | 72 | 1,718,137 | 0 | 5,714,035 |
| sdk-ts | deepseek-chat(DeepSeek 官方) | 156 | 876,695 | 0 | 12,970,240 |

结论:
- Claude 模型在 OhMyAgent 里的缓存已是最佳形态(无缓存输入每请求个位数)。
- ZYB 报的本月 Opus 用量(无缓存输入 1.7 亿、缓存读 14.5 亿)远大于本机全部 Opus 记录(缓存读约 3.4 亿、无缓存几千),说明该 key 还有其他使用方,本机无法归因。
- 非 Claude 模型经 ZYB(Anthropic 协议透传,OhMyAgent 不改请求体)命中率低:deepseek-v4.1-flash 约 17%,gpt-6-astra 约 77% 且有多次 10 万级整段未命中。前缀已证明稳定,问题在 ZYB 转底层 OpenAI 协议时的缓存亲和。

可优化点(未实施):
1. 标题重复生成:CLI `generate_session_title` 用主模型(实测 Opus,约 1.2k 无缓存输入/会话),客户端 `TitleGenerator` 又用小模型生成一次且被适配器标题覆盖。
2. 网关只转发 `anthropic-version/anthropic-beta/accept`,丢掉了 Claude Code 的 `X-Claude-Code-Session-Id`、`User-Agent: claude-cli/…`、`x-app`;第三方网关常用它们做会话亲和。是否改善 ZYB 命中率需用 ZYB key 做 A/B(本次被权限拦截,未测)。
3. 配额耗尽(429 quota exceeded)时 Claude Code 仍按退避重试约 10 次、耗时 3 分钟,不耗 token 但界面长时间无响应。
